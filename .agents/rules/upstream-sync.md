# Upstream Sync Rules

This repository is a fork of `QuantumNous/new-api`. It has diverged on purpose in the areas listed below, so upstream changes are merged deliberately: adopt what fits, adapt what touches a diverged area, ignore what targets removed code. `AGENTS.md` defines when this file must be read (see **Upstream sync (mandatory read gate)**). Rules use the same MUST / Do NOT wording as `AGENTS.md`.

## Remotes

- `origin` is this fork. `upstream` is `https://github.com/QuantumNous/new-api.git`; add it if missing (`git remote add upstream https://github.com/QuantumNous/new-api.git`).
- Sync by merging `upstream/main` into `main` with `git merge --no-ff upstream/main`. Do NOT rebase fork history onto upstream, and do NOT replace a sync with cherry-picks: merge commits keep each sync point visible and make the next merge base correct.
- Do NOT push a sync, or merge it into `main` from another branch, until the maintainer approves.

## Fork divergences

Each area below differs from upstream by design. Keep the fork's design when resolving changes in these areas.

| Area | This fork | Where |
|------|-----------|-------|

The web console is the separate repository `Herta-Network/new-api-frontend`, deployed on a static host; it brings in upstream's `web/` by its own `.agents/rules/upstream-sync.md`. | Model pricing | Model metadata and pricing share one workspace under `/admin/models`. Prices are edited through a simple real-price form that writes billing expressions, with the expression editor as the advanced mode. | Desktop | Electron is removed. | — |
| Modules | Fork-owned domains are modules under `internal/module/` with an arch-tested boundary; the rest keeps upstream's layout as the shared kernel. Modules write kernel tables only through `model/module_api.go`. | `internal/module/`, `internal/arch/`, `model/module_api.go` |
| Relay hardening | Non-stream answers copy only the upstream headers in `clientUpstreamHeaders` (content type and disposition, the Codex headers), never ones naming the upstream provider or account. Bedrock clients send each call once (`aws.NopRetryer`), leaving retries to channel retry. A channel that disables store sends `store:false`, and a request to a native Responses upstream gets it even when the client left `store` out; a request converted to another format keeps only the `store` the client sent. A converted stream whose upstream stopped before its own terminal event ends with `response.failed` or a Claude `error` event, never a synthesized `response.completed` or `message_stop` (`helper.UpstreamEndedEarly`), and a stream that already started ends with `helper.StreamErrorData`; a Gemini stream carrying only a prompt block reason ends as content filtered. Upstream bodies read whole go through `service.ReadUpstreamBody` (`MAX_RESPONSE_BODY_MB`) or `service.ReadUpstreamErrorBody` (1 MiB); read new upstream bodies with them, not `io.ReadAll`. A body past the limit is not retried on another channel. | `service/http.go`, `relay/channel/aws/relay-aws.go`, `relay/common/relay_info.go`, `relay/responses_request.go`, `relay/helper/stream_result.go` |
| Channel routing | One `service.ChannelRouter` per request routes every attempt: groups (one group, or the Auto groups in order) → priority tiers from the highest → within a tier, weighted rendezvous hashing of the request's routing seed (`service/route_seed.go`), with the key of a multi-key channel ranked the same way. A failed attempt's key is never chosen again; after any failure but a 401, 403, 429 or invalid key its channel is also passed over until the group's other candidates were tried, and only then are its other keys used. The next attempt takes the best remaining candidate; `RetryTimes` caps the attempts in a group. An Auto request skips a group that has no candidate at all, with or without cross-group retry; only cross-group retry moves on from a group whose candidates were all tried or whose budget ran out, and the next group starts a fresh budget. The seed is a session rule's key, a session header, `prompt_cache_key` or `metadata.user_id`, the system prompt and tools, or the first user message, scoped to the user and model; requests without one draw by weight. There is no retry-indexed priority tier, no channel affinity cache, and no `RetryParam`; affinity rules are seed sources and parameter override templates only, and `strict` holds only a request that carries earlier turns. 429 cooldowns are kept per key for multi-key channels. Both cache paths list candidates through `model.ListRouteCandidates` and weigh them alike. Routing writes `admin_info.routing` to logs. The task plugin endpoint decides between plugin and relay channels with `Peek`, which records nothing and keeps no seed, so the distributor routes after conversation recognition; a Responses WebSocket create seeds its route from its own payload (`SetSeedBody`). | `service/channel_router.go`, `service/route_seed.go`, `service/channel_select.go`, `service/channel_affinity.go`, `model/channel_route.go`, `model/channel_rate_limit.go`, `controller/relay.go`, `middleware/distributor.go`, `relay/responses_websocket.go` |
| Fork features | OpenCode Go channel (type 64), thinking-signature repair, 429 cooldown, Coding Plan usage, conversation session recognition (`internal/module/conversation`), fast GPT token counting in `tokenkit/`, per-user payment rate limits, SMTP sender parsing, log and `quota_data` I/O tuning, the Redis key prefix (`REDIS_KEY_PREFIX`), model mappings that hide upstream names from users. | various, `common/redis_key_prefix.go`, `relay/helper/model_mapped.go` |

## Classify before merging

List the incoming commits (`git log --oneline $(git merge-base main upstream/main)..upstream/main`) and decide for each one before resolving anything:

- **Adopt as-is:** relay and channel adaptors, `relaykit/`, `tokenkit/`, task plugins (`pkg/jsplugin/`, `plugins/tasks/`), the billing engine and settlement, security fixes, dependency and toolchain bumps, bug fixes in shared code, and new i18n strings.
- **Adapt:** anything that touches a diverged area. Keep the upstream intent and express it in the fork's design, following the rules below.
- **Ignore:** everything under `web/`, which new-api-frontend brings in by its own sync rules, and changes that only touch removed code, such as the console-serving code listed under Console, SQLite or MySQL code paths and docs, Electron, Creem, Waffo, Waffo Pancake, the old top-up and subscription payment endpoints, the retired currency display options, `ratio-settings-card.tsx`, the old group editors, or the payment compliance acknowledgement. Ignore the code, not the behavior: if the fix applies to a fork equivalent, port it there.

## Resolving changes by area

- **Console:** keep `web/` deleted. Before committing the merge, run `git rm -r -q --ignore-unmatch web`: upstream's new `web/` files merge in without a conflict, and changed ones conflict as modify/delete. Drop the frontend steps upstream adds to `Dockerfile`, `makefile`, and `.github/workflows/`, and the frontend parts of README changes. Port an upstream change to the console page the backend served (analytics injection, its Content-Security-Policy) to new-api-frontend (`src/lib/static-hosting.ts`). An upstream change to `pkg/billingexpr/testdata/frontend_simulation.json` or `service/testdata/group_rules_cases.json` is adopted here and then copied with `bun run contracts:sync` in new-api-frontend.
- **Database:** keep only the PostgreSQL branch of any dialect switch. Remove references to `common.MainDatabaseType`, `common.SetDatabaseTypes`, `common.SQLitePath`, `DatabaseTypeSQLite`, and `DatabaseTypeMySQL`. Rewrite upstream SQLite/MySQL/PostgreSQL matrix tests as a single PostgreSQL test on the package database (`pgtest.Reset`), or on a fresh schema (`pgtest.NewSchema` / `pgtest.NewSchemaDB`) for migration tests. GORM may silently drop clauses on PostgreSQL that MySQL honors (for example `Limit` on `Delete`, or on `Count` without a subquery), so check the generated SQL of any such upstream query.
- **Schema changes:** upstream changes the schema through model fields and GORM tags, additions to the `AutoMigrate` list in `migrateDB`, and Go functions that reshape tables before `AutoMigrate`. Adapt them: keep the model and tag change, add a migration with `make migration` that creates the same schema (`TestMigrationsMatchModels` lists anything missing), add a new model to `schemaModels` in `model/migrate_test.go`, and do not bring in the `AutoMigrate` list entry or the reshaping function. Port a data backfill as SQL in the same migration, or as an idempotent startup step in `migrateDB` when it needs Go. Upstream tests that build an old upstream schema and upgrade it apply only through the baseline: start them from the baseline migrations, or drop the case.
- **Payments:** port upstream fixes to shared concepts (quota limits, subscriptions, top-up quota conversion) into `internal/module/payment/`. Follow the **Payments** rules in `AGENTS.md`. Never reintroduce removed providers or endpoints.
- **Currency:** translate old fields to the unified ones. Backend `operation_setting.USDExchangeRate` maps to `currency.ResolveRate`, and the console's mapping is in new-api-frontend's sync rules. This applies to upstream tests too.
- **Console routes:** server-built console links point into `/user` or `/admin`. For any new top-level console route upstream adds, update server-built links and `reservedRouteNamespaces` in `pkg/jsplugin/routing.go`.
- **Tests that assert removed UI:** drop only the assertion that targets the fork's intentional difference, and keep the rest of the test.
- **Modules:** upstream never changes `internal/module/`, but an upstream commit can touch the kernel functions `model/module_api.go` wraps (`creditTopUpQuota`, `getSubscriptionPlanByIdTx`, the user quota cache, `lockForUpdate`) or the kernel tables a module reads. Keep the wrappers' signatures and behavior in step when resolving it, and keep new fork code out of the kernel: follow **Modules** in `AGENTS.md`.
- **Conversation sessions:** `service/channel_affinity.go` (the `conversation_session` key source of routing seed rules) and the OpenCode Go adaptor (`relay/channel/opencodego/`) read the recognized session through the kernel helper `service.ConversationSessionID`, which calls the resolver the conversation module's middleware stores under `constant.ContextKeyConversationSessionID`. An upstream change to those files must keep calling that helper; never import `internal/module/conversation` from them. Upstream routes that relay chat, responses, messages or Gemini requests keep `conversationhttp.ConversationSession()` before `Distribute()`.
- **Channel routing:** keep routing in `service.ChannelRouter`. When upstream changes `GetRandomSatisfiedChannel`, `GetChannel` in `model/ability.go`, `CacheGetRandomSatisfiedChannel`, `RetryParam`, the auto-group context indexes or the channel affinity cache, port the intent into the router (`Next`, `Fail`, `Remaining`) and do not bring the removed functions back. New upstream call sites select with `service.SelectChannelForRequest(c, model)` or `service.RouterFor(c).Next`, prepare the attempt with `SetupContextForSelectedChannel(c, choice.Channel, choice.Key, model)`, and in a retry loop call `router.Fail` before `DecideRelayRetry(c, err, router.Remaining(c))`. New channel filter kinds go through `ChannelSatisfiesFilters` as before. From upstream changes to affinity rules, adopt key sources and parameter override templates; ignore TTL, cache size, `switch_on_success`, `keep_on_channel_disabled` and cache endpoints (`BuildRequestPolicy` accepts and drops those options). A new multi-key mode applies only to requests without a routing seed. Extend `service/channel_router_test.go` and `controller/channel_pin_retry_test.go` when upstream adds a routing rule.
- **Redis:** `REDIS_KEY_PREFIX` works through a go-redis hook on `common.RDB` (`common/redis_key_prefix.go`) that prefixes every key, the KEYS of EVAL, the MATCH pattern of SCAN, and PUBLISH channels, so upstream's Redis code stays unchanged. Keep new upstream Redis usage on `common.RDB`, never a second client. Lua scripts must receive every key in KEYS and must not build key names or take them from ARGV. A command missing from `redisKeyRanges` fails while a prefix is set: add it with the key positions `COMMAND INFO` reports. SUBSCRIBE and PSUBSCRIBE bypass hooks, so pass their channel names through `common.RedisChannel`, as `pkg/wsmanager` does, and compare received channel names with the same. The hook rewrites arguments in place, so do not use `ScanCmd.Iterator()` or process a command twice. Extend `e2e/redis_key_prefix_test.go` when upstream adds a Redis path.
- **Model lists and mappings:** users never learn which channel serves a model or the upstream name a channel maps it to. `owned_by` in model lists is the model's vendor, else `system`; upstream's channel-type owner (`channelOwnerName`, `GetPreferredModelOwnerChannelTypes`) is removed, so do not bring it back. Abilities and the channel cache come from `Channel.OfferedModels`, which leaves out the channel's mapped upstream names. `helper.HideMappedModel` rewrites model names in relay responses and errors, and `is_model_mapped`, `upstream_model_name` and `response_model` stay in the admin part of log `other`. When upstream adds a model list, a response path, or a user-visible log or task field, keep it on these rules and extend `TestModelMappingHidesUpstreamModels`, `TestRelayResponsesRewriteKeepsBodyWhole`, `TestUserLogsHideMappedUpstreamModel` or `TestTaskLogDTOHidesChannelAndMappedModelFromUsers`.
- **Docker image:** `.github/workflows/ghcr-image.yml` compiles the binary on the runner and passes it to the Dockerfile as the context named `builder`, which replaces the Dockerfile's builder stage. When upstream changes that stage (Go version, its `ENV`, `-pgo`, `-ldflags`), make the same change in the workflow's Build binary step. The step takes Go from `go.mod`, so keep the `golang` image tag at the same version. Changes to the runtime stage need nothing in the workflow.
- **Third-party notices:** when upstream bumps a dependency listed in `THIRD-PARTY-LICENSES.md`, update its version there.
- **Protected project information:** follow `AGENTS.md`; never alter it while resolving.

## After the merge

- Keep the merge commit to conflict resolution and the adaptations needed for it to build and pass tests. Put larger follow-ups, such as supporting a new upstream feature in a fork-only UI, in separate commits after the merge.
- Sync new-api-frontend to the same upstream commit in the same round, by its own sync rules, and report which upstream console changes depend on backend changes in this merge.
- Run the full verification:
  - `go build ./...` and `go vet ./...`
  - `GOWORK=off go build ./...` in `relaykit/` and `tokenkit/`
  - `TEST_POSTGRES_DSN=… make test`
  - when upstream changed models, migrations, or indexes, the PostgreSQL 18 fresh-and-upgrade verification from **Database compatibility** in `AGENTS.md`
- If an upstream change touches billing as defined in `AGENTS.md`, read `.agents/rules/billing.md` (and `pkg/billingexpr/expr.md` for expressions) before resolving it.
- Report the result to the maintainer:
  - the incoming commits grouped as adopted, adapted, and ignored, with the reason for each adaptation or omission
  - every conflict and how it was resolved
  - follow-up commits
  - the verification commands and their results

  Then wait for approval before pushing.
